## Confirmed root causes

### Shared backend — empty driver/vehicle projection

`publish-customer-live-trip` selected `trips.*` only. `confirmed_driver_id` filled `assigned_driver_id`, but `driver_first_name`, vehicle make/plate/colour, and photos stayed **null** because nested `driver`/`vehicle` were never hydrated.

iOS Local Activity therefore showed **Assigned** with blank identity. `heading_to_pickup` copy still used title **“Driver assigned”**, so status appeared stuck.

### iOS MK-261116-011 — no APNs update path

Live Activity **did** appear (local ActivityKit via foreground JS). Subsequent remote updates require `customer_live_activity_tokens`. Table was empty because upsert unique key was `(customer_user_id, device_id, trip_id)` and NULL `trip_id` rows do not conflict in Postgres — registrations failed to stick / never landed.

Without an activity update token, APNs fanout is a no-op → Activity stuck on first local ContentState.

### Android MK-261116-012 — FCM never reaches native notify

`LiveTripFcmReceiver` (C2DM BroadcastReceiver) is insufficient once `ExpoFirebaseMessagingService` owns `MESSAGING_EVENT`. Device channel `onecab_live_trip_v1` can be DEFAULT while `mLastNotificationUpdateTimeMs=0` (never posted).

FCM HTTP acceptance ≠ display. Data-only HIGH priority messages must be handled in a `FirebaseMessagingService` subclass that posts the ongoing notification **without JS**.
